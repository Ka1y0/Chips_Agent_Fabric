# Planning and local-model boundary audit: 2026-09-05

Baseline: `06edc4a543820411c902d5f2a22ef3ec9bb78926` on
`integrate/personal-intelligence-fabric-v0.3`, Draft PR #1.

## Scope and interpretation

This is a focused source/contract review of Hybrid Engine, cluster expansion, local-model
profiles, and the semantic Bridge policy, informed by the machine entrypoint and architecture
documents. It is not a complete repository security audit or real-host deployment acceptance.
No provider authentication, model inference, machine enrollment, or runtime tuning is performed.

Supervisor owns canonical state and concrete Worker routing. Hybrid Engine describes HOW work
is decomposed; ClusterPlanner expands stages; the Scheduler must still decide WHICH eligible
Worker executes each instance. Bridge remains optional, derived, and non-authoritative.

## Corrected boundaries

### Whole-plan privacy preflight

Previously, local capability checks considered only the top-level request. A private research
panel could pass with `research` alone even though its generated planning and synthesis stages
required `reasoning`, and an independent review could require `verify-result`.

The preflight now checks the union of the request and every generated stage's requirements.
Missing capabilities are sorted in the explanation. Private plans remain blocked when any required
capability is missing; remote fallback and Bridge remain disabled. This check establishes only
capability coverage, not Worker health, independent-review capacity, locality authorization, or
current availability. Those still require per-stage Scheduler/runtime enforcement.

### Explicit Computer Use requirements

The fixed Computer Use template previously discarded request-specific hard capabilities. Standard
capabilities now stay with their specialist stages; extra requirements, such as `control-browser`,
constrain the Actor. Blank explicit capability IDs are rejected at request construction. This
conservative rule does not imply a new real browser or OS execution backend.

### Routing intent survives DAG expansion

Latency, quality, and cost weights previously existed on ClusterStage but disappeared from stage
instances and serialized protocols. Both now retain an additive `routingWeights` object. Non-finite,
negative, boolean, and zero-total weights are rejected at stage construction. These are routing
preferences for a future dispatch integration, not permissions or a separate Worker-selection engine.
No measured throughput improvement is claimed by preserving this metadata.

### Local-model uncertainty remains explicit

`supports_reasoning=None` now projects to `reasoningMode=unknown`, distinct from explicit `False`
(`unsupported`) and `True` (`onDemand`). Capability flags accept only booleans or None, so strings
such as `"false"` cannot become asserted capabilities by Python truthiness.

Unknown memory pressure no longer authorizes recommendations for increased concurrency or full
GPU offload. Measured maximum parallel capacity is still retained as evidence; the recommendation
remains one until memory headroom is known. Existing observed GPU offload settings are preserved,
not silently changed. Profiles remain recommendations with `adaptiveMutation=false`.

### Credential-free local endpoint values

Configured discovery and direct LocalRuntimeCandidate construction share the same validation.
Endpoints must be explicit loopback HTTP(S), with valid nonzero ports when supplied, no user info,
query parameters, fragments, backslashes, whitespace, or raw controls. Validation errors do not echo
the rejected endpoint. IPv4, localhost, and bracketed IPv6 loopback remain supported.

Python's URL parser does not validate application safety and can remove control characters before
parsing. Raw-input checks therefore precede parsing and the port attribute is explicitly validated.
See the [Python URL parsing security documentation](https://docs.python.org/3/library/urllib.parse.html#url-parsing-security).
Discovery still opens no sockets. This is not a complete SSRF boundary for a future network client:
redirect handling, DNS resolution, authentication and response-size limits require separate checks.

## Compatibility and regression gate

The package version and database migrations are unchanged. `routingWeights` is additive;
`reasoningMode` gains the explicit `unknown` value. Endpoint strings containing query parameters or
userinfo are intentionally no longer accepted. Integrators should not place authentication in URLs.

`tests/test_planning_safety_regressions.py` covers valid paths as well as the failures above, without
modifying or relaxing the earlier test assertions. The full existing CI workflow remains required,
including all isolated subprocess acceptance jobs. Exact run IDs and outcomes are recorded in the
PR discussion, not inferred from a lack of failure notifications.

## Remaining integration work

- `cheapFirstEscalation` currently names a single-stage planning choice. It is not an implemented
  evidence-triggered cheap-model-to-strong-model retry loop.
- Local runtime discovery and profile recommendations do not yet provide automatic live model
  probing, freshness-aware benchmark learning, or safe transactional parameter application.
- Cluster blueprints still need explicit integration with durable per-stage scheduling, including
  privacy flags, reviewer independence, resource leases, quotas, cancellation, and routing weights.
- Real OS/browser/VLM Computer Use and autonomous elastic scale are not established by offline tests.
- Semantic Bridge mode selection and source accounting do not by themselves implement every codec
  or a measured multi-model information-sharing system.

The next useful vertical slice is an opt-in local model probe feeding timestamped observations into
one durable, policy-checked task, with a verified result and cancellation path. Keep this separate
from claims of zero-touch installation or unrestricted machine control.
